# GCRA 平滑限流的虚拟调度与有界等待

## 题面

网关对新上线的导出接口做限流后，整点批量任务被硬性拒绝，客户端拿不到任何可重试时间；另一个租户把等待队列占满，后到的请求一直挂到连接超时。限流参数改过三次，值班只能靠猜来估等待时间，业务侧的重试退避与网关给出的到期时间始终对不上。运维还发现空闲很久的键一直留在内存里，状态表随租户数增长只增不减；并发压测时同一键的两次申请偶尔会同时放行，实际速率超过配置。落点在 gsb/batch49-go-safety-b-15 的 gcra_throttle.go，类型 GcraThrottle，需要把虚拟调度、突发容忍、有界等待与空闲回收做成一致的限流器。入口 NewGcraThrottle(cfg GcraConfig) *GcraThrottle，立即裁决 Take(key string, units int) (Decision, error)，有界等待 TakeWait(ctx context.Context, key string, units int) error，重置 Reset(key string) error，读取 Usage(key string) Usage 与键列表 Keys() []string，回收 Prune() int，推进逻辑时钟 Advance(ms int64) 与 Clock() int64，快照 Snapshot() ([]byte, error) 与 Restore([]byte) error。

需要落实的判断与边界：1) 每键维护理论到达时间与突发容忍额度，立即裁决按申请单位数扣减虚拟时间；2) 拒绝要给出精确等待毫秒数，拒绝时 TatMs 保持原值、剩余单位按当前额度给出，客户端按返回的等待时间重试即可通过；3) 空闲时间按速率折算回可用额度，折算后按整数单位向下取整，额度有上限，不能无限累积；4) 单次申请单位数超过突发容忍上限要直接拒绝，不得拆成多次等待分批放行；5) 等待模式有最大等待上限，超限立即返回 ErrWaitTooLong；6) 等待期间该键被重置后，等待方必须按新的理论到达时间重新计算，不得沿用旧值；7) 键状态压缩的判定依据是最后一次放行的理论时间，不是最后一次访问时间；8) 并发下同一键的裁决串行，跨键互不阻塞，同键并发申请放行数恰好等于突发额度；9) 空键与纯空白键报 ErrBlankKey、非正单位数报 ErrBadUnits，未知键的 Usage 返回零值，Keys 按字典序输出，放行与拒绝计数按申请单位数累计；10) 重置要清掉该键的理论到达时间与放行、拒绝计数，重复重置保持幂等；11) 快照保存逻辑时钟与每键状态，损坏快照返回 ErrBadSnapshot 且不动现网，恢复后继续按原时钟裁决。

硬约束：同键的读改写必须串行、跨键不得互相阻塞，放行判定与计数更新属于同一次原子切换；快照与裁决互斥，恢复成功前旧状态继续服务；键表与等待队列都有上限，空闲回收不得把仍在等待的键提前清掉。
